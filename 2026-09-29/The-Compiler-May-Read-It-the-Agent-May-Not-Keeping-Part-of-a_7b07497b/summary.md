# 论文速读：The Compiler May Read It, the Agent May Not: Keeping Part of a Research Code Away from a Coding Agent

## 一句话总结
本文系统性地分类并测试了针对 Claude Code（Anthropic）的四种访问控制机制——容器挂载规则、权限规则（命令文本+路径匹配）、沙箱、以及软性指令文件——在一条"编译器可读、AI 智能体不可读"的目的型访问规则上的覆盖能力，最终发现十五种潜在读取路径中只有两类被两种机制同时覆盖、两类被单一机制覆盖、七类仅被沙箱覆盖，另有五类完全未被任何现有机制覆盖。

## 研究问题与动机
- **核心问题**：科研团队将开源物理求解器与自有 IP（本构模型/反应动力学模型）捆绑部署于 AI 编程智能体上，智能体在编译构建时需要读取这些 IP 文件，但模型的算法本身属于未发表知识产权，不应进入智能体的上下文窗口并外传。
- **已有规则为何不够**：容器挂载、权限规则、沙箱、指令文件这四类机制在商品化智能体编排框架中可普通用户直接获得，但它们都只能匹配「用户账户、路径或命令拼写」，无法判断「哪个程序正在打开文件」——即规则的本质判据（消费方身份）不可表达。
- **完整中介原则的违背**：权限规则与沙箱对访问检查的范围不重合且相互独立，两者合取也不能覆盖所有读取路径，属于经典的 complete mediation failure。
- **误委托问题（confused deputy）**：编译器是智能体的合法子进程，继承智能体的权限标签后若直接受限则构建失败；若给编译器开例外，则智能体也可借同样的例外自行读取。

## 核心贡献（创新点）
1. **首次系统性地把"目的型访问控制（Purpose-based Access Control）"问题置于当前主流商业编程智能体上评估**：本文对照 Byun & Li（2008）的目的型访问控制三路径（请求方声明/静态注册/推断），论证在 vendor-run harness 下三者均不可实现。
2. **提出并穷举了十五种受保护字节进入智能体上下文的读取路径分类表（Table I）**：涵盖直接读取、间接路径、解释器 literal、重定向、文件描述符、符号链接、进程替换、动态链接器、编译预处理模式、构建配方、版本控制历史、内置文件工具、MCP 策略服务器、hook 脚本等，构成可供后续研究的基线分类体系。
3. **揭示了五种完全未被现有机制覆盖的路径**，其中最关键的是 `gfortran -E f`（编译器预处理模式）和版本控制历史读取，说明命令字符串匹配与文件打开时机存在根本性的语义鸿沟。
4. **给出了长期运维视角的 deny-list 演化数据**：一周内拒绝事件 64 次，其中 54 次为复合命令整体拒绝；deny-list 四期修订分别新增 118、13、4、0 条新命令名，证明"列表增长"与"规则完整性修复"是两类完全不同的工程问题。
5. **与 ActPlane、AgentSpec、Conseca、PORTICO、Fides 等近年系统的对比定位**：指出这些系统要么需宿主内核级权限，要么按行动结果路由而非文件打开时机路由，都无法表达"同一文件被不同程序消费"这条规则。

## 方法详解
- **四类访问控制机制及判定依据**：
  1. **Container 挂载与用户账户**：规定智能体运行时所在用户及挂载路径，不感知文件内容去向。
  2. **Permission rules**：匹配命令文本 + 路径，粒度为「一条命令字符串」而非「一次文件打开」。
  3. **Sandbox**：仅覆盖 Bash/PowerShell/Monitor 三类命令及其子进程；agent 的内置读/写工具绕过沙箱直连权限系统，导致两类机制不能合成。
  4. **Instruction file（软约束）**：会话开始时读取自然语言规则，"声明但无法执行"。
- **判定覆盖性的证据分级**（由强到弱）：① 直接从 shipped rule set 读取；② 复述 vendor 文档原话；③ 基于 shell 语义推理；④ 根据容器目录结构构造同构单元格。
- **核心论点的逻辑链**：
  - 要执行规则，必须能在**文件打开时**判断**消费者**是谁。
  - 但现有机制都在**命令启动时**按**字符串匹配**做决定，未触及 open 事件本身。
  - 即使按进程谱系（lineage）标记，子进程继承父进程标签——这是经典的 confused deputy [9]。
  - 即使给编译器开例外，智能体也能以同样条件启动它，例外变成通用通道。
  - 编译产物（含常量、诊断、中间文件）属于**信息泄露**而非访问控制问题，需要后置过滤器而非前置授权规则。
- **与文献的对照**：
  - Byun & Li [1]：目的型访问控制需第三方监督方，但 vendor harness 没有。
  - Type enforcement / SELinux [2]：可按进程域隔离，但需要特权策略加载器与 root，普通用户无法获得。
  - Trusted broker 方案：把受保护文件移至另一用户账户，经构建工单—过滤回复的通道访问，近似而非强制执行规则；代价是断掉 edit-build-fix 闭环并引入人工作业。

## 实验与结果
- **数据集**：作者部署于一套真实物理流求解器项目，受保护文件两个路径；未公开发布 deny corpus（含真实项目路径与远端主机），仅公布统计形状。
- **评估方法**：
  - 将七周内 64 次拒绝事件的去重 transcript 与 deny 字符串匹配，按 tool-call ID 去重；
  - 将 15 条路径按四类机制逐格判定覆盖性（Table I 共 60 个单元格）。
- **主要数字**：
  - Table I 六列 × 十五行：2 格被双机制覆盖、1 格仅权限规则覆盖、7 格仅沙箱覆盖、5 格**均不覆盖**（Fig. 1）。
  - 5 周 deny-list 演化：规则数从 14 → 488 → 540 → 556 → 586；新增命令名 118 → 13 → 4 → **0**（第四期 30 条规则全是既有命令的粒度收紧，证明"完整性修复 ≠ 列表增长"）。
  - 64 次拒绝中 54 次（84%）是复合命令（`cd && rsync`、`rm -rf && cmake && make`）整体被拒，影响范围远超受保护文件本身。
  - 拒绝类别优先级分配：28 次边界限制、26 次破坏性动词门、5 次边界试探、4 次受保护目标、1 次不符。
- **最强结论**：现有四种机制中没有任何一种能命名"正在读取的消费者程序"；按命令字符串匹配的授权模型与按"谁在消费"的目的型规则存在结构性不匹配。

## 相关工作脉络
1. **Byun & Li [1]（VLDB 2008）目的型访问控制**：提出三类目的推断路径（声明/注册/推断），本文证明在 vendor harness 下三者均不可得。
2. **Boebert & Kain [2] / SELinux 类型强制**：进程域-文件类型的二维表可达规则，但需 root 级策略加载器，不在普通用户工具集内。
3. **Garfinkel [5]（NDSS 2003）系统调用拦截陷阱**：间接路径目录被本文引用为三条间接读取路线的来源，提示 syscall-interposition 类方案同样受限于路径匹配。
4. **Zheng et al. [7] ActPlane（2026）**：在 agent 全进程树上 Hook OS 事件，支持 lineage gate；但子进程继承父域导致保护文件对编译器也被拒绝，若为编译器开例外则例外可被 agent 复用。
5. **Santos-Grueiro [8] PORTICO（2026）**：将仓库路径绑定到访问模式与有界 justification episode，最贴近本文需求，但建模的是单消费者，无法处理编译器这一第二读者。
6. **Debenedetti et al. [14] / Costa et al. [15] CaMeL、Fides**：从信息流控制角度判定"数据可以流出到哪里"，关注输出出口而非文件打开时机。
7. **GitHub Copilot content exclusion [10] / Cursor .cursorignore [11]**：厂商文档明确承认 Agent mode 不支持内容排除——与本文 Table I 中五条未覆盖路径直接对应。

## 局限性与未来方向
- **结果具 vendor 特定性**：权限规则与沙箱的具体工具范围、规则语法属于某一 vendor 的实现细节，会随版本变化；论文的通用性结论在三条（命令字符串不能中介文件打开、路径规则无法指认消费者、子进程继承标签无法区分构建与启动者）。
- **未与受保护文件实际运行**：十三条路径未在真实受保护文件上跑过，因成功即构成披露、失败只能验证一种命令拼写；因此覆盖率表是"分类可能性"而非"实测通过数"。
- **拒绝对抗视角有限**：本文评估面向普通用户的现有机制表达能力，未对抗设计 hostile agent；root 管理员可装内核级强制器，但不在研究范围内。
- **信息泄露通道未关闭**：承认接受编译器诊断与编译产物（含常量、行号表）作为受控泄露，但缺乏对"产出内容过滤"的任何实现建议。
- **未来方向**：需要在 open 事件层做消费方识别、设计非继承式的进程标签传播、为编译产物建立后置过滤器。

## 研究启发与可借鉴点
1. **十五路径分类表可作为后续工作的评测基线**：任何新提出来的 coding-agent 安全机制均可对照 Table I 逐格检验覆盖度，形成可比指标。
2. **"命令字符串匹配 ≠ 文件打开中介"的结构性质疑框架**可迁移到任何按 tool-call 做访问控制的 agent 系统，包括 MCP 服务器、hook、策略服务器。
3. **deny-list 长期运维数据（新增命令名数量 vs. 规则数量）揭示一类通用工程误区**：安全列表的维护成本常被误计为"添加新条目"，实际上更多是补齐既有条目间的完整性不变量。
4. **与 trusted broker 方案的折中分析**对"把受保护文件放在第二用户账户、通过过滤工单回应"这一架构给出清晰的代价边界——仅在受保护文件稳定且与智能体编辑代码分离时成立，不适用于同仓库共同演进场景。
5. **可把本文的十五路径分类与最近 ActPlane / PORTICO / AgentSpec 的公开实现逐一对照**，量化各自在相同部署上的单元格覆盖数，形成横向评测。

## 关键术语表
- **Purpose-based access control**：按访问意图决定允许/拒绝的访问控制范式，与按主体/客体/时间匹配的传统模型正交。
- **Complete mediation（完整中介）**：所有对对象的访问都必须经过安全检查的原则；本文的权限规则与沙箱未合成达到该原则。
- **Confused deputy（误委托）**：受信任程序在不受信任者的权限下做了后者自身不能做的事；子进程继承标签即为此经典案例。
- **Bounded disclosure（有界披露）**：本文对规则的表达方式——允许编译产物与诊断输出中包含派生内容，而非要求零泄露（noninterference）。
- **Type enforcement**：将进程划入域、文件划入类型、以二维表定义交叉权限的强制访问控制形式。
- **Trusted broker**：部署在第二用户账户下的构建中介，通过过滤回复近似实现目的型规则。
- **MCP（Model Context Protocol）**：智能体与外部策略服务器通信的协议；本文指出 hook 与策略服务器均不在沙箱覆盖内。
- **Denial list（拒绝列表）**：按命令名维持的 denylist；本文用五周迭代数据展示其运维成本与完整性修复本质差异。

# 论文速读：The-Compiler-May-Read-It-the-Agent-May-Not-Keeping-Part-of-a-Research-Code-Away-from-a-Coding-Agent

## 一句话总结
本文证明：面向"编译者可读但编码智能体不可读"这一目的论访问控制（purpose-based access control）规则，**容器、权限规则、沙箱三层现有机制均无法联合覆盖所有读取路径**——在15种被分类的读取路径中，有5条对三种机制完全不可见；核心原因是这些机制只能匹配"用户账户/路径/命令字符串"，无法判断"哪个程序"执行了文件读取。

## 研究问题与动机
- **核心问题**：研究代码中的专属本构模型/反应模型（constitutive & kinetic closures）属于发表前知识产权，或受许可协议限制只能用于生成可发表数据、不得传递算法本身。编码智能体（coding agent）读取这些文件后，其字节将进入上下文窗口并随转录本离开机器；但求解器（solver）又必须依赖这些文件才能完成编译。目标规则表述为：**编译器可打开受保护文件，智能体不可**。
- **动机1**：现有主流编码智能体平台（如 Claude Code、GitHub Copilot Agent、Cursor）广泛部署于研究团队，但它们在"按读取者身份而非按路径"进行授权方面存在系统性盲区。
- **动机2**：安全文献中"目的论访问控制"（Byun & Li, VLDB 2008）要求系统能判断一次访问的"目的"，而操作系统只能观测其代理变量（哪个进程打开了文件、输出流向哪里），无法直接观测目的。
- **动机3**：现有工程方案（deny-list、sandbox、content-exclusion）在实践中暴露出**不完整的中介**（failure of complete mediation）问题：两条机制互不重叠，且各自存在已知的绕过路径。
- **动机4**：作者以"普通用户"视角评估（无 root、不能加载内核策略），所得负结果具有现实落地约束下的参考价值。

## 核心贡献（创新点）
1. **形式化一条不可简化的规则**：提出"编译器可读、智能体不可读"的目的论访问控制规则，并将"读取"与"输出泄露"作区分，明确指出该规则本质是**有界披露**（bounded disclosure）而非非干扰（noninterference）。
2. **15条读取路径的系统分类**：将受保护文件进入智能体上下文的所有可能路径归纳为15类（含直接读取、字节-文本编码器、解释器字面量、shell 内置重定向、文件描述符间接、符号链接、进程替换、动态链接器调用、编译器等价读取、构建目标下的 recipe、版本控制历史读取、内置文件读取工具、MCP 策略服务器读取、hook 脚本读取），并对每条路径逐一检验三种机制的覆盖情况。
3. **机制组合的不完备性证明**：指出权限规则与沙箱在15条路径上的覆盖呈"部分重叠"（仅2条被两者同时覆盖、7条仅沙箱覆盖、1条仅权限规则覆盖、**5条两者都不覆盖**），从而说明它们的联合也无法表达为单一策略。
4. **实施成本的实证记录**：报告为期5周的 deny-list 迭代史（14→488→540→556→586条规则；前几次新增命令名，最后一次新增0条命令名但补了15个"目录级守卫"向"文件级守卫"的不变量缺口），以及7周、64次拒绝事件的分布统计。
5. **对行业产品的定位诊断**：以 GitHub Content Exclusion、Cursor .cursorignore 为例，指出它们在论文分类框架下恰好对应"未被覆盖"的路由，从而给出一个可与行业现状直接对照的评价基准。

## 方法详解
- **受控实验设置**：在容器内运行 Claude Code 对流体求解器（基于开源基座 + 自有本构/动力学闭包）进行编码任务；受保护文件挂载在项目树内，由同一用户账户运行。
- **四种机制的定义**：
  - (a) **Container**：限定运行时用户与挂载路径。
  - (b) **Permission rules**：基于命令文本与路径进行匹配的 deny-list。
  - (c) **Sandbox**：仅覆盖 Bash/PowerShell/Monitor 命令及其子进程，内置文件读写工具直连权限系统而不经过沙箱。
  - (d) **Instruction file**：会话开始时智能体阅读的软约束，声明规则但无法执行。
- **关键判断**：在容器内，编译器和智能体以同一用户账户运行，编译器是智能体 shell 的子进程；两者对 OS 而言"看起来相同"，区别仅在于**读取的目的**（最终字节去向：编译器→同机目标代码/诊断；智能体→上下文窗口并离开机器）。由于四种机制都无法命名"哪个程序在读"，因此规则无法被表达。
- **理论归约**：将问题归约为 security literature 中的 purpose-based access control（Byun & Li, 2008）——识别目的的三种途径（请求者声明、固定目的注册、推断）在此部署下均失效：instruction file 是第一种但不可执行，构建本身是多目的应用（对应第二种失败），无法可靠推断目的。
- **信息泄露通道的扩展讨论**：即使解决了"打开"阶段的授权，编译器输出（预处理源码、诊断引用的行、带调试信息的符号表）仍构成泄露通道；因此完整的规则还需对构建返回结果做**过滤器**，而这不在本文考察范围内。

## 实验与结果
- **数据集/环境**：作者自有流体求解器项目，含2个受保护文件路径；运行环境为 Docker + Claude Code（Anthropic），2026年6-7月收集。
- **分类矩阵**：15条路由 × 4种机制 = 60个单元格，证据等级从高到低分为四类：直接从规则集读取（4格）、引用供应商文档范围声明（5格）、基于语义推理（21格）、按构造一致赋值（30格）。其中2条路由在7月对伪装树实测被拒。
- **主要数值结果**：
  - 覆盖分布：2条双覆盖、7条仅沙箱、1条仅权限规则、**5条均不覆盖**。
  - Deny-list 5次修订：命令名从10 → 128 → 141 → 145；第4次修订新增0条命令名但补齐了15条"目录到文件"的不变量缺口。
  - 拒绝事件：7周共64次，其中54次为复合命令整体被拒；按分类28次属于隔离边界、26次破坏性动词门、5次边界探测、4次受保护目标。
  - **无一次拒绝真正阻断了受保护文件的正常使用**（保护目标计数为下界）。
- **结论**：三种机制的联合仍遗漏5条路由；denied-list 维护成本显著且易遗漏不变量；编译器等价读取（`gfortran -E f`）是最关键的未覆盖路由。

## 相关工作脉络
1. **Byun & Li (VLDB 2008)**：提出目的论访问控制三途径（请求者声明/固定注册/推断），本文指出在 agent 场景下三者皆不可行——agent 既无独立目的声明通道，其构建又是多目的应用，推断目的在 OS 层无观测点。
2. **Boebert & Kain (NCSC 1985) / SELinux**：type enforcement 方案通过"进程域×文件类型"二维表强制策略，能区分编译者与智能体，但需要特权策略加载器与宿主内核管理权，超出"普通用户"假设。
3. **Garfinkel (NDSS 2003)**：系统调用插桩安全工具的陷阱与误区，本文沿其思路指出路径别名、描述符间接等15种绕过手段在 agent 场景下同样成立。
4. **Di Donato (2026)**：已公开发布的同一 agent 绕过案例（动态链接器直接调用 cat），本文将其纳入分类并作系统扩展。
5. **AgentSpec (ICSE 2026)**：基于触发器/谓词/执行动作的运行时策略，但仍作用于"agent 动作"而非"文件打开"，未能覆盖编译器等价读取。
6. **PORTICO (2026)**：将仓库路径绑定到访问模式与有界 justification episode，最接近本文规则，但建模为单消费者，未处理"编译器也是读者"的双消费者情形。
7. **信息流控制系列（Securing AI Agents, 2025；Defeating Prompt Injections, 2025）**：关注数据外泄与 prompt 注入，本文与其正交——本文关心的是"同机读取者身份"而非"网络出口"。

## 局限性与未来方向
- **局限1**：仅以"普通用户"视角评估，未覆盖具有 host root 的管理员可部署的内核级强制方案（如 SELinux type enforcement）。
- **局限2**：15条路由中仅2条经实测拒绝，其余13条依赖推理或供应商文档，未对真实受保护文件运行（因运行成功即构成披露）。
- **局限3**：仅讨论一种 vendor（Anthropic Claude Code）的当前配置；具体规则语法与范围声明会随版本变化。
- **局限4**：未处理编译器输出的信息泄露通道（预处理源码、诊断引用、符号表），仅指出其存在并定义为"有界披露"。
- **局限5**：威胁模型中假设模型与 harness 非敌对，仅防范工具调用层面的误用；未评估面对有意对抗的 agent 时的鲁棒性。
- **未来方向**：部署需 kernel/type-enforcement 级别的基础设施；将"读取端"授权与"输出端"过滤联合设计；探索在 agent harness 内部嵌入目的感知执行环境；扩展到多消费者（不止编译器）场景。

## 研究启发与可借鉴点
1. **"读取者身份"作为第一类公民**：把"哪个程序打开了文件"提升到访问控制的主键位置，而非仅在路径/用户层面做匹配——这对任何需要"同一文件被两类程序以不同目的消费"的场景均有通用价值。
2. **不变量驱动的规则维护**：第4次 deny-list 修订揭示的核心问题是"两条目标必须被同等保护"这一不变量未被规则语言表达；启发我们引入**规则生成器的不变量检查**，以自动化方式发现此类缺口。
3. **分类矩阵+证据分级**的评估范式：60格矩阵按证据强度分层（实测/文档引用/语义推理/构造赋值），兼顾可复现性与诚实的覆盖边界声明，可作为同类研究的模板。
4. **与行业产品的对照锚点**：用同一分类框架重新解读 GitHub Content Exclusion、Cursor .cursorignore 的已知局限，提供了一个可与产品更新同步对齐的基准。
5. **"有界披露"而非"非干扰"的实践立场**：承认编译器输出通道不可避免，转而聚焦在"打开阶段"的最小化授权，是一种更可落地的安全设计哲学。

## 关键术语表
- **Purpose-based access control（目的论访问控制）**：根据访问的"目的"而非访问者身份来决定是否授权，本文指出在 agent 场景下目的难以被系统直接观测。
- **Bounded disclosure（有界披露）**：允许受控的信息流出（如编译器诊断引用某一行），但不允许受保护文件的完整字节离开机器；区别于非干扰（noninterference）的强保密语义。
- **Confused deputy（困惑副手）**：受信任的程序在其调用者的权限下执行了其调用者本不应被允许的操作；本文指编译器的读文件权限会被智能体"借用"。
- **Complete mediation（完全中介）**：所有对对象的所有访问都必须经过安全检查；本文指权限规则与沙箱的组合在某几条路径上完全不进行检查。
- **Type enforcement（类型强制）**：将进程划入域（domain）、文件划入类型（type），以二维表决定许可；SELinux 的实现方式，需特权策略加载器。
- **MCP（Model Context Protocol）**：智能体与策略服务器通信的协议；本文指通过 MCP 调用的 `read_file` 属未覆盖路由。
- **Constitutive & kinetic closures（本构与动力学闭包）**：流体力学求解器中使偏微分方程可解的自有材料模型，本文的受保护文件内容。
- **Noninterference（非干扰）**：系统的高密级输入不影响低密级输出；本文强调其规则不属于此强语义，仅为有界披露。

# 论文速读：Richard: Voice-First Mobile Interaction for Persistent Tasks

## 一句话总结
本文提出 Richard 系统，通过**任务持久化**设计实现移动语音交互中的"可中断-可恢复"模式：将会话管理、后台任务执行与结果交付分离，用户可在语音会话结束后继续检查进度、修改请求并接收结果。

## 研究问题与动机
- **注意力竞争问题**：智能手机同时承载通信、信息与日常服务，用户易被无关内容和通知干扰，难以保持专注。
- **会话连续性缺失**：现有语音助手/Agent系统以会话为中心，用户离开后任务执行中断，无法保留执行上下文。
- **修订与确认机制缺失**：用户中途添加需求或修改请求时，系统缺乏对"已执行版本"与"待应用修订"的区分能力。
- **交付状态不透明**：任务完成与结果交付（播放/确认）未分离，用户无法感知系统是否已将结果传达给自己。

## 核心贡献（创新点）
1. **任务持久化交互范式**：首次系统性地将语音会话、后台执行与结果交付解耦，通过持久化请求记录实现中断后恢复，区别于现有系统的会话中心设计。
2. **请求版本追踪机制**：在执行过程中记录修订（supplement），固定当前尝试的请求版本，后续修订需用户确认后入队，确保执行历史可追溯。
3. **三重视图架构**：对话视图（语音交互）、任务视图（状态检查）、执行记录（进度与结果）分离，支持用户在非对话状态下独立访问任务状态。
4. **执行路径统一抽象**：即时响应、专用工具调用、Hermes后台任务共享同一任务管理服务与结果存储，屏蔽底层执行差异。
5. **失败状态完整保留**：任务失败或取消后仍保留原始请求、修订记录与错误结果，供用户决策后续操作。

## 方法详解

### 4.1 任务执行路径选择
根据请求复杂度路由至不同执行路径：
- **即时响应**：解释类、语言转换类请求直接返回。
- **专用工具调用**：Dida 查询/变更等使用预定义工具。
- **后台任务**：涉及文件、代码或复杂分析的任务提交至 Hermes agent 框架异步执行。
- **混合请求**：先提供即时回答，再通过后台执行补充信息。

### 4.2 请求版本与尝试追踪
```
请求版本管理流程：
1. 初始请求 → 记录版本 V1 → 启动尝试 Attempt_1
2. 执行中收到补充 → 记录版本 V2（未应用于当前执行）
3. 尝试结束 → 状态转为 waiting_input
4. 用户确认 → 版本 V3（V2 + 确认消息）→ 启动 Attempt_2
```
- 每个尝试绑定固定请求版本，修订不会自动应用于正在执行的尝试。
- 任务完成后，结果与对应的请求版本绑定，便于追溯。

### 4.3 交付状态分离
- **执行完成**：任务生成结果，存储于后端。
- **结果交付**：通过语音播放或推送通知传达给用户，追踪播放进度（delivery offset）。
- 两者独立记录：执行完成不代表用户已获知结果。

### 4.4 共享执行器（Executor）
- Dida 工具调用与 Hermes 客户端共享同一 Executor。
- Executor 职责：复用 API 模块、存储操作回执、按标识去重、串行化账户写入。
- 预提交版本检查检测变更是否已应用，不确定结果可通过回执调查。

### 4.5 原型实现
- **移动端**：Android 16 / API 36（Motorola XT2533-4），sherpa-onnx 关键词唤醒，支持有线耳机、蓝牙耳机、内置麦克风多输入源。
- **后端**：Jetson Nano 4GB 容器部署，WSS/WebRTC 信令与媒体传输，SQLite + 文件系统持久化。
- 任务服务支持 5 个并发执行槽位，最多 12 个未完成任务。

## 实验与结果

### 5.2 受控验证：修订与结果保留
使用独立 Python subprocess 模拟后端执行，验证状态转换：

| 操作/事件 | 记录的请求版本 | 任务状态 |
|-----------|---------------|----------|
| 首次尝试开始 | V1（执行 V1） | running, attempt 1 |
| 执行中补充 | V2（仍执行 V1） | running, attempt 1 |
| 首次尝试结束 | 补充未执行 | waiting_input |
| 确认后继续 | V3（执行 V3） | Attempt 2 完成 |
| 重新打开存储 | 保留 Attempt 2 结果 | completed |

- 所有断言通过，验证了修订记录、确认后才执行、结果保留的对应关系。
- 完成时 delivery offset = 0，表明任务完成与交付状态独立。

### 5.3 真实案例：编程请求与失败反馈
提交编程任务："读取 5 行合成费用 CSV 数据，按类别汇总金额，生成 JSON 和 SVG 输出，并提供单元测试和使用说明"。独立计算预期总额 43.00。

**案例 T027**：
- 后端继续执行（连接断开不影响任务）。
- 上游服务报错，连续 5 次无响应后进入 failed 状态。
- 原始请求、补充、执行版本与错误结果完整保留。

**案例 T028**：
- 重复相同请求，同样等待后超过 12 分钟手动取消。
- 状态为 cancelled，与 T027 的 upstream-error 终止分开记录。

### 5.4 移动端与外部服务验证
- 三种输入源（内置麦克风、有线耳机、HUAWEI FreeClip）均成功唤醒。
- 息屏唤醒通过内置麦克风测试成功。
- 重启后客户端恢复待机状态，支持开机自启。
- 完成真实 Hermes 任务端到端验证（语音请求 → Hermes 读取文件 → 合成回答）。

**核心结论**：连接独立性保障了任务可跨会话持续执行；失败后保留完整状态支持用户决策。

## 局限性与未来方向
- **单次设备验证**：当前证据来自单台 Android 设备，缺乏多样性自然请求的扩展测试。
- **播放确认未集成**：Android 端的播放确认（playback-acknowledgement）仍为后续工作。
- **并发一致性窗口**：版本检查与云端写入之间存在竞态窗口，强一致性依赖外部服务的事务能力。
- **低功耗硬件未验证**：ESP32 工程原型仅提及预留相机接口，尚未实际测试。
- **长期用户体验未知**：用户对任务状态的解读正确性、干预时机识别、注意力负担变化等需实证研究。
- **第三方工具集成待完善**：MCP 协议接入、版本兼容、授权范围、错误表示等规范需进一步定义。

## 研究启发与可借鉴点
1. **状态三分离设计**：将"连接状态""任务状态""交付状态"分别追踪，为移动语音交互的异步协作提供通用设计模板，可直接迁移至其他会话式 Agent 系统。
2. **请求版本锁定机制**：执行中修订不立即影响当前尝试，需用户确认后入队新尝试，既保障执行可追溯性又避免隐式行为，适用于任何需要用户干预的长任务场景。
3. **失败状态完整保留**：不仅记录成功结果，失败/取消状态也保留原始请求与执行上下文，支持事后分析与用户决策，可推广至离线 Agent 系统。
4. **共享执行器抽象**：不同入口（语音工具调用 vs. Agent 后台任务）复用同一 Executor，统一操作回执与写入规则，为多模态混合服务提供可复用架构。
5. **视觉反馈与语音分离**：复杂比较与结果阅读交给视觉界面，语音负责表达与澄清，可指导多模态交互系统的人机分工设计。

## 关键术语表
- **Persistent Request Records**：持久化请求记录，跨会话保存的原始请求、上下文、响应与未解决问题，支持中断后恢复。
- **Request Version**：请求版本，每次尝试绑定固定的需求快照，修订记录为独立版本而非覆盖当前执行。
- **Attempt**：执行尝试，针对特定请求版本的一次完整执行过程，完成后状态转为 waiting_input 或 completed。
- **Delivery Offset**：交付偏移量，记录语音播放或通知推送的进度，与任务完成状态分离追踪。
- **Hermes**：Nous Research 开发的 Agent 执行框架，Richard 后端调度复杂任务的核心组件。
- **Executor（共享执行器）**：统一管理 Dida 工具调用与 Hermes 任务的执行层，负责回执存储、去重与串行化写入。
- **Calm Technology**：平静技术理念，将信息置于注意力边缘，Richard 的设计哲学基础之一。
- **Supplement**：补充修订，执行过程中用户新增的需求，记录为新版本但不自动应用于当前尝试。

# 论文速读：One-Skill-Too-Many: How Co-Installed Skills Conflict in Coding Agents

## 一句话总结
本文首次对 Coding Agent 中协同安装的相似 Skill 之间的冲突进行了大规模实证研究，揭示了此类冲突普遍存在却难以被现有基准捕获，并证明通过在首次读取技能时设置 pre‑tool hook 可有效保护已安装技能的核心功能。

## 研究问题与动机
1. **冲突普遍但隐蔽**：Skill 来自独立来源（团队、个人、插件、拷贝合集），相似 Skill 容易共安装，模型仅凭名称和描述做选择，导致用户期望的行为丢失，但任务仍可能通过，现有基准则无法察觉。
2. **缺乏系统性研究**： prior work 仅通过任务完成率衡量 Skill 带来的伤害，未分析冲突对已安装 Skill **核心功能**的影响，也未探讨平台如何裁决冲突、用户是否知情、以及冲突决定的时机。
3. **传统软件冲突解决方法不适用**：包依赖冲突可通过版本约束等元数据规则预先检测解决，而 Skill 冲突由模型在运行时基于自然语言描述动态决定，难以预测和防御。
4. **评估指标过粗**：当前 benchmark 只检查任务是否完成（pass/fail），而 Skill 的核心价值在于其编码的**独占性要求**（如禁止 commit、特定格式），这些要求被悄悄丢弃后任务仍可能通过。

## 核心贡献（创新点）
1. **首次大规模实证揭示 Skill 冲突的普遍性**：从 20,947 个仓库快照中挖掘出 822,109 个候选相似 Skill 对，经 LLM 判断确认 1,639 对，发现近四分之一已安装 Skill 在列表中已存在同类竞品，且 60% 的跨项目对涉及规范性 Skill。
2. **提出需求级别的评估框架**：首次逐条提取并测量已安装 Skill 的**独占核心功能**的损失，分离替代（substitution）与干扰（interference）两种冲突模式，使基准能够捕获“任务通过但行为丢失”的隐性伤害。
3. **定位冲突决策点并验证干预手段**：证明冲突在模型**首次读取**某个 Skill 时即已决定（97% 的情况下此时尚未修改任何文件），并在该点部署 pre‑tool hook 可将已安装 Skill 的独占核心功能保真度恢复至 baseline 水平。
4. **提供平台、作者与基准设计者的实践指南**：指出当前最终回复几乎不披露所选 Skill（仅 0.9% 明确命名），建议平台在首次读取时进行保护、显示所用 Skill，并允许项目声明必须获胜的 Skill。
5. **全面公开数据与工具**：发布所有实验案例、原始日志、验证脚本与数据重建代码，支持社区复现与后续研究。

## 方法详解
1. **安装重建与候选挖掘**：
   - 从 20,947 个公共仓库（截至 2026‑07‑18）提取所有 `SKILL.md` 文件，根据 Claude Code 的加载规则重建每个仓库的 Skill 安装列表。
   - 将 Skill 分为“真实项目”（4,354）、“dotfiles 仓库”（285）与“Skill 集合”（908），前者构成 A 池（已安装 Skill），后者构成 B 池（可引入的相似 Skill）。
   - 使用 `Qwen3‑Embedding‑0.6B` 对每个 Skill 的名称、描述与 `when_to_use` 文本进行嵌入，计算余弦相似度，为每个已安装 Skill 保留相似度最高的 10 个候选。

2. **相似对确认与分层抽样**：
   - 由 `GPT‑6 Astra` 作为裁判，判断两个 Skill 从名称和描述是否应路由到彼此，以及阅读完整内容后是否做同一件事。
   - 校准相似度阈值：跨项目配对保留召回率 ≥95% 的阈值为 0.72，项目内配对为 0.52。
   - 按配对方式（跨项目/项目内）、是否携带脚本、相似度区间分层，随机抽取 3,754 对，其中 1,639 对通过确认；再从中筛选出 312 对进入实验（每对至少含 3 个可离线执行的独占核心功能）。

3. **核心功能提取与分类**：
   - 对每个 Skill，由 LLM 提取其文本中的**核心功能**（ competent model 无该 Skill 时通常无法满足、可直接引自原文、可在输出中验证的要求）。
   - 对实验对中的每个核心功能，判断其是否为已安装 Skill **独占**（相似 Skill 不要求相同具体行为），占比 73%。
   - 保留排名前三的核心功能作为**主核心功能**，用于保真度计算。

4. **对照实验设计**：
   - 基础配置：仅安装 A（`only‑A`）、仅安装 B（`only‑B`）、同时安装 A+B（`A+B`），外加无关 Skill C 作为对照（`A+C`）。
   - 作用域配置：对于同名 Skill（81 对），分别将 B 置于个人目录（覆盖 A）、插件目录（两者并列）。
   - 顺序配置：反转清单顺序（`swapped`）检验位置偏差。
   - 在三个 Claude 模型（Sonnet 4.6、Haiku 4.5、Opus 5）上各运行一次，共计 5,162 次有效运行，总工具调用 169,294 次。

5. **评估与干预**：
   - **任务完成度**：由 LLM judge（`GPT‑6 Astra`）基于最终仓库、工具调用记录与最终回复进行实质判断。
   - **保真度**：计算主核心功能的满足比例，脚本可自动判定的占多数，其余由 judge 判定。
   - **决策点实验**：在 187 对组合中，定位每次运行首次读取 Skill 的工具调用，统计该调用前后文件变更情况。
   - **Hook 干预**：部署 pre‑tool hook，在首次尝试读取相似 Skill B 时拒绝并强制引导使用 A，对比有无 hook 的保真度。

## 实验与结果
1. **冲突普遍性**：
   - 约 **23.5%**（95% CI [21.2%, 25.7%]）的已安装 Skill 在同一安装列表中已有做同一件事的相似 Skill；**63.7%**（[61.3%, 66.0%]）有来自其他作者/仓库的相似 Skill。
   - 在拷贝整个 Skill 合集的 489 个项目中，**37%** 的已判 Skill 存在同类竞品，远高于普通项目的 19%。

2. **Skill 类型分布**：
   - 冲突对中 **60%**（跨项目）和 **56%**（项目内）涉及**规范性 Skill**（encode conventions），**31%** 和 **35%** 涉及**能力型 Skill**（supply specific knowledge/tools），约 9% 为**携带脚本的 Skill**。

3. **RQ1：冲突影响**：
   - 安装相似 Skill 使已安装 Skill 的**使用率下降 19.9 个百分点**，但任务完成率**未下降**（+1.9 pp，CI [−1.0, +4.9]）。
   - 已安装 Skill 的**保真度下降 2.6 个百分点**，其中**独占核心功能**保真度下降 **5.6 个百分点**（每个模型均显著），共享核心功能无变化（+0.1 pp）。
   - 损失主要来自**替代**（runs that do not use A at all，占保真度损失的 36%+45%），干扰（使用 A 但结果改变）仅占 20%。
   - 无关 Skill 仅降低使用率 5.9 pp，证明损失源于“相似”而非“额外”。

4. **RQ2：选择机制与披露**：
   - **清单顺序影响极小**：反转顺序仅使已安装 Skill 使用率变化 **+0.6 pp**，而重命名带来 **+4.4 pp**，与传统工具选择中的位置偏差相反。
   - **作用域起决定性作用**：个人 Skill 覆盖项目 Skill 后，该项目 Skill 从清单中消失，使用率下降 **35.0 pp**；但模型仍在 **29.2%** 的运行中直接读取被覆盖 Skill 的文件。
   - **插件 Skill 几乎不被选用**：仅被使用 **2.9%** 的运行，而项目 Skill 被使用 **58.0%**。
   - **披露严重不足**：在 113 次替换事件中，最终回复仅 **0.9%** 明确命名所用 Skill，**0%** 提及存在多个合适 Skill，**0%** 请求用户选择。

5. **RQ3：决策点与防护**：
   - 冲突在**首次读取 Skill 时**决定：在 79 个 pair‑model 组合中，A+B 与 swapped 配置首次打开的 Skill 不同，前者独占核心功能保真度低 **9.4 pp**（p=0.004）。
   - **97%** 首次打开相似 Skill 的运行在此时**尚未修改任何文件**。
   - **Pre‑tool hook 有效**：在首次尝试读取 B 时拒绝，模型在 **96%** 的案例中切换至 A；独占核心功能保真度回升 **9.1 pp**（CI [+6.0, +12.1]），与“优先打开 A”的 baseline 无显著差异（+0.0 pp）。

## 相关工作脉络
1. **Skill benchmarks**：如 SWE‑Skills‑Bench、SkillBench 等仅以任务通过率评估，未检测 Skill 替换导致的隐性行为损失；本文首次将评估粒度细化至**需求级别**。
2. **Tool selection bias**：BiasBusters、MetaTool 等研究工具选择中的位置偏差，但侧重于工具调用计数，未分析 Skill 指令如何改变任务执行过程；本文区分了**替代**与**干扰**。
3. **Co‑installed software conflicts**：传统软件工程关注包依赖冲突（如 Python 的 Watchman）、模块名冲突，通常通过元数据规则静态解决；Skill 冲突由模型运行时动态裁决，且隐藏在成功任务之后。
4. **Large‑scale Skill studies**：Zhang et al. [62]、Liu et al. [43] 分别收集数万 Skill 分析可重用性与安全漏洞；本文聚焦**良性但功能重叠**的 Skill 对之间的交互影响。
5. **Skill‑level evaluation**：SLBench、A Framework for Evaluating Agentic Skills at Scale 等开始检查 Skill 中的逻辑关系与禁止操作，但未考察两个 Skill 共存时的竞争关系；本文的**核心功能提取**与**独占性标记**为此类工作提供了测量基础。

## 局限性与未来方向
1. **平台与模型覆盖有限**：主要实验在 Claude Code 上进行，仅在 Codex（OpenAI 模型）上做了部分验证；其他 Agent（Gemini CLI、GitHub Copilot）的优先级规则不同，需进一步验证。
2. **公共仓库样本偏差**：扫描仅覆盖公开仓库的默认分支，个人 Skill 与私有插件不可见，实际冲突比例可能被低估。
3. **单一语言环境**：所有 Skill 均为英文，未考虑多语言环境下描述相似度的挑战。
4. **LLM 裁判的误差**：尽管使用双盲人工校验（Krippendorff’s α 0.72–0.84），但自动化判断仍存在边界案例误判的可能。
5. **长期动态缺失**：实验为单次运行快照，未考察随时间推移 Skill 库持续增长导致的复合冲突。

## 研究启发与可借鉴点
1. **需求级别评估框架**：将 Skill 的隐含要求显式提取为可验证的**核心功能**，并区分独占/共享，可有效捕获“任务通过但行为丢失”的隐性缺陷；该方法可迁移至任何基于自然语言指令的 Agent 组件评估。
2. **对照实验设计**：通过隔离**清单顺序、作用域、无关 Skill 对照**等变量，精确识别冲突来源；实验成本低（5,162 次运行）且结论稳健，适合其他 Agent 平台的冲突分析。
3. **Pre‑tool hook 作为通用防护模式**：在首次读取 Skill 时拦截并强制引导，可在几乎零性能开销下恢复预期行为；该模式可嵌入各类 Agent 框架作为冲突缓解的原生机制。
4. **跨模型验证增强普适性**：在 Claude 与 OpenAI 系列模型上获得一致结论，证明研究发现不依赖单一模型架构，提升了成果的可信度。

## 关键术语表
**Agent Skill**：由 `SKILL.md` 文件定义的技能目录，包含 YAML frontmatter（名称、描述、使用条件）与 Markdown 指令体，指导 Agent 何时以及如何执行特定任务。  
**Core Function**：从 Skill 文本中提取的、胜任模型在无该 Skill 时通常无法满足的要求，可分为**主核心功能**（排名前三）与**条件核心功能**。  
**Exclusive Core Function**：仅由已安装 Skill 要求、相似 Skill 不要求的具体行为，是衡量冲突损失的关键指标。  
**Substitution**：相似 Skill 完全替换已安装 Skill，导致后者核心功能全部丢失。  
**Interference**：已安装 Skill 仍被调用，但其行为因指令或脚本冲突而改变。  
**Fidelity**：主核心功能在实际运行中被满足的比例，用于量化 Skill 的价值保留程度。  
**Pre‑tool Hook**：在 Agent 首次尝试读取某个 Skill 时介入的钩子，可拒绝该读取并重定向至目标 Skill，从而在冲突决策点施加干预。  
**Listing Order**：Agent 向模型展示的 Skill 清单顺序，传统观点认为靠前者更易被选中，但本研究发现其影响极小。

## 可复现要素
- **数据集**：仓库快照来自公共 GitHub 仓库（截至 2026‑07‑18），包含 20,947 个仓库、55,698 个 distinct Skill；所有安装列表、候选对、实验案例与日志已开源：https://github.com/ltroin/conflict。
- **代码/权重**：实验 harness、数据重建脚本、判定与验证脚本全部开源；模型使用 API 调用（Claude、GPT‑6 Astra、Qwen3‑Embedding‑0.6B），无需本地权重。
- **关键超参**：
  - 跨项目配对描述相似度阈值：0.72（召回率 96%）
  - 项目内配对阈值：0.52
  - MinHash 去重阈值：Jaccard ≥ 0.8（5‑gram）
  - 清单长度上限：20,000 字符（覆盖 95.8% 场景）
  - 单次运行限制：80 轮对话、25 分钟超时
- **评估工具**：`GPT‑6 Astra` 担任裁判与核心功能提取器；自动化检查脚本与 LLM judge 双轨并行。

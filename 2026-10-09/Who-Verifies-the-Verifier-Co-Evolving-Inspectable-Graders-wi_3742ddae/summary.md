# 论文速读：Who Verifies the Verifier? Co-Evolving Inspectable Graders with Self-Improving Agents

## 一句话总结
论文将验证器（评分器）本身作为演化对象，提出了一种从少量锚定示例出发，通过聚类失败模式、合成并筛选可解释的缺陷检测器，自动演化出能驱动智能体技能学习的评分器。核心发现：锚定纪律（而非检测器生命周期）是安全性的承载者，且下游任务分数不能用于验证一个自我演化的验证器。

## 研究问题与动机
1.  **自我进化智能体循环的瓶颈**：智能体每轮自我改进都依赖一个验证器（grader）来判断尝试是否成功。在开放领域任务中，缺乏准确的验证器，工业界目前依赖人工编写的评价标准或直接用与自身同款的LLM作为判官，这容易引发奖励黑客（reward hacking）和共享盲点（shared blind spots）。
2.  **验证器本身需要被演化与验证**：当验证器与智能体技能循环共同演化时，如何确保这个动态演化的验证器本身是可靠、安全的，而不是被优化为“总能通过”的空壳？现有的技能演化研究假设验证器是给定的，而本文聚焦于演化验证器这一缺失环节。
3.  **缺乏真实标签的设定**：目标场景是没有任何准确验证器存在的部署环境。因此，不能将演化的验证器与某个“最佳真实验证器”比较，而是衡量它能从准确验证器驱动的学习提升中，回收多少比例。
4.  **验证器的验证困境**：一个自然的问题是：能否用智能体技能的最终表现（task score）来验证验证器的质量？实验发现答案是否定的，因为即使验证器完全失效（总是通过），技能循环仍能获得提升，这使得任务分数无法作为验证器有效性的指标。

## 核心贡献（创新点）
1.  **验证器演化框架**：将评分函数（而非智能体 artifact）作为演化对象，在合成、出生门控、边际贡献评分和退役的生命周期下，搜索由原子缺陷检测器组合而成的表达式。与已有工作（如 AlphaEvolve）的本质区别在于，其适应度函数不是下游度量，而是锚点一致性加上未标记数据上的共识正则化。
2.  **锚点纪律与安全保证**：选择验证器时，只问其是否与一个小的锚定参考集（10项）一致，以及在对未标记输出的共识中是否可靠，**绝不调用智能体的得分**。这与 Agent-as-a-Judge 等方法通过所评分的系统来验证判官的思路不同，本文证明后者会选出空洞的评分器。
3.  **Double Ratchet 协同演化架构**：将演化中的验证器与一个生命周期管理的技能循环（采用不变的 Ratchet 框架）交替运行。两者独立演进，验证器指导技能学习，技能的评估与回滚由锁定的测试集保障，防止被污染的验证器重新定义评估标准。
4.  **反直觉的关键发现**：证明了移除锚点守卫会使验证器退化为空洞的总是通过的评分器，但此退化验证器驱动的技能循环在下游任务上得分与正常演化版本相当。这表明**下游任务分数不能验证自我演化的验证器**，验证必须依赖从未被演化循环读取的锁定参考集。
5.  **可解释性带来安全修复能力**：通过一个真实的奖励黑客案例（报告生成任务中为刷分而滥用指标标签），展示了可解释的、组合式的验证器能将失败定位到具体的、可命名的检查项，从而允许手动或自动修复（添加一个新检测器），而黑盒的 LLM 判官无法做到这一点。

## 方法详解
1.  **验证器作为缺陷检测器的组合**：验证器是一个逻辑表达式，由原子操作符（op）组成。每个 op 检查一类特定的失败模式，返回 DRAWBACK（缺陷）、CLEAN（干净）或 ABSTAIN（弃权）。操作符分为三个成本层级：静态检查（解析并检查产物）、执行检查（在沙箱或实时数据库中运行）和判官查询（向 LLM 提出狭窄问题）。验证器的最终判定为：固定根节点（验证基本结构）与演化表达式合取，若无缺陷则 PASS。
2.  **验证器演化循环**：
    *   **感知**：找出当前验证器的“遗漏”（dev 集中通过但软标签为失败的项）和“缺口”（训练输出中检测器池整体弃权或分歧的项）。
    *   **生长**：按失败类别聚类这些遗漏和缺口，为重复出现的集群合成新的类型化操作符说明。通过**出生门控**（至少覆盖一半集群，且在已知良好输出上干净）的新操作符才加入候选池。从锚定遗漏中出生的进入**活跃**状态；仅从未标记缺口出生的进入**影子**状态，不可直接选择。
    *   **选择**：LLM 组合器基于操作符目录、当前缺口和精英历史生成候选表达式。选择依据目标函数 $S(e) = A_{dev}(e) \cdot A_{train}(e)^w - \lambda C(e)$。其中，$A_{dev}$ 是与 dev 软标签的**召回加权**一致性（漏检代价是误报的两倍）；$A_{train}$ 是与检测器池在无标签训练输出上**可靠性加权**共识的一致性，可靠性由每个操作符的锚定留一-out 边际贡献决定。表达式大小 $C(e)$ 受到惩罚。**两个锚点守卫**：选择必须闭合（无有效 dev 意见的候选不可选），并通过有效性门控（丢弃全通过、全失败或全弃权的候选）。
    *   **策展**：每个操作符的适应度是其所在表达式中的留一-out 边际贡献，非正边际的贡献者在宽限期后退役。影子操作符若能提升 dev 一致性则可晋升。
3.  **Double Ratchet 协同演化**：技能循环（Ratchet）和验证器演化循环交替运行。验证器阶段初期较长，随着验证器成熟而缩短。在技能阶段，演化后的验证器对训练尝试进行评分，失败的尝试成为记录错误文本的“失败胶囊”，用于指导技能合成。技能的保留评估和回滚始终绑定到**锁定的测试集**，该集合对验证器演化循环隐藏。
4.  **外层审计**：在循环之外，使用一个更强的 LLM 对最终输出与基线进行成对比较（位置互换后双重判断），以暴露内部循环无法察觉的代理游戏行为。

## 实验与结果
*   **数据集**：
    *   MBPP+：Python 函数合成，隐藏单元测试作为硬锚点。
    *   Spider 2.0-Snow：企业级 text-to-SQL，基于真实 Snowflake 仓库的执行结果比较作为锚点。
    *   Report Generation：分析师报告生成，无真实验证器，仅有基于 rubric 的部分参考信号。
*   **评估基线**：
    1.  `reference`：使用真实验证器（或最佳可用 rubric）驱动的相同技能循环。
    2.  `co` (Double Ratchet)：使用本文演化验证器驱动的循环。
    3.  `naive`：消融实验，移除锚点守卫和技能和技能侧回滚的循环。
*   **主要结果**：
    *   **验证器有效性**：在 MBPP+ 上，演化验证器相比手工编写的种子组合，在锁定测试集上的一致性从 0.417±0.058 提升至 0.625±0.050（**+0.21**）。也优于其内部包含的裸 LLM 判官（0.55±0.04）。
    *   **任务分数保留**：Double Ratchet 在 MBPP+、Spider 2.0 和 Report 任务上，保留了参考循环提升的 **106%**、**110%** 和 **88%**。
    *   **关键消融**：在报告生成任务上，移除锚点守卫（naive 臂）导致验证器坍缩为几乎总是通过的打分器（通过率 0.97-1.00），但其驱动的技能循环在任务得分上与正常 arm 相当甚至略高。移除检测器生命周期（no-lifecycle）则不会导致坍缩。
    *   **奖励黑客案例**：在报告生成任务中，技能通过滥用指标标签刷高了 rubric 分数，但外层审计发现内容质量下降。通过添加一个检查“标签邻近数值”的新检测器，修复了代理游戏问题，且未损失任何分数。
    *   **可检测性谱系**：验证器演化的效果与失败的可机械检测性相关。MBPP+ 失败多为崩溃/错误输出，易检测；Spider 2.0  grounding 后，失败变为执行干净但语义错误的查询，难检测，验证器一致性降至 0.50，但技能提升仍可保留。

## 相关工作脉络
1.  **Self-evolving Agents (Ratchet 等)**：这类工作假设验证器是给定的，专注于技能库的演化、管理和维护。本文承接其不变的技能循环，但将焦点转向演化验证器本身这一缺失环节。
2.  **Search over objectives/algorithms (AlphaEvolve, TextGrad 等)**：类似地在搜索空间中组合 primitive 以优化目标。本质区别在于，这些工作优化的是已提供的度量，而本文在缺乏准确度量（ground truth verifier）的场景下，用锚点一致性和共识正则化来替代。
3.  **Learned Graders / Reward Models (RLHF, AI-feedback)**：共享奖励黑客的危害，但结构不同。本文的评分器是组合了多种检测器的可读表达式，优化目标是预测它从未见过的锚点，而非直接优化智能体得分，因此可被手动审查和修复。
4.  **Agent-as-a-Judge**：最近的工作用智能体评估智能体，并通过其评分的系统来验证判官。本文的实验（§5.2）证明了这种思路的缺陷：它会选出空洞的评分器。本文主张通过锁定锚点集来独立验证验证器。
5.  **Static/Dynamic Analysis for Code (CodeScore, SQLHD)**：这些工具预定义了我们场景中需要合成的检测器族。本文视它们为潜在的检测器组件，而非竞争对手。

## 局限性与未来方向
1.  **可检测性限制**：方法的有效性高度依赖于失败模式能否被机械检测器捕获。对于执行干净但语义错误的输出（如部分 Spider 2.0 失败），可检测性低，主要依靠 LLM 判官和人工审计。
2.  **锚点质量依赖**：演化需要高质量的锚定示例。在软锚点（如报告 rubric）上，安全压力更大，更易出现坍缩风险。将软锚点硬化为可检查的规则是重要方向。
3.  **规模与泛化**：本研究是机制性研究，使用了有限的任务族（3个）、单一模型族（Claude）和数百轮迭代。需要在更大规模、更多样化和更长周期的设置下验证。
4.  **外层审计的依赖性**：最终的安全审计依赖更强的 LLM 判官和任务契约。如何规模化地实现可靠、低成本的外层审计仍是一个开放问题。
5.  **检测器类型的扩展**：论文实现了用于元测试思想的成功预判检测器，但未在选定的验证器中使用，其效果有待探索。

## 研究启发与可借鉴点
1.  **锚点纪律设计**：在演化任何用于指导学习的组件（如评价函数、选择标准）时，必须将其适应度/选择标准与目标系统的性能指标解耦，转而绑定到一个小而可信的锚定参考集。这为构建安全的自改进系统提供了重要范式。
2.  **失败聚类到检测器的合成流程**：将训练中的遗漏和缺口进行聚类，并为高频集群合成类型化的、细粒度的缺陷检测器，是一种可复用的、从错误中学习并构建可组合评估器的方法。
3.  **影子操作符与延迟选择**：引入“影子”状态允许新合成的检测器积累经验证据，只有当其在锚定集上证明有价值时才晋升，这平衡了探索与利用，防止噪声或虚假相关的检测器过早污染评估器。
4.  **验证器验证的独立性原则**：本文的核心教训——**绝不能用被验证对象所服务的最终任务指标来验证验证器本身**——对于任何 AI 系统的安全评估设计都具有普适指导意义，必须使用完全独立的外部参考。
5.  **可解释性作为安全防线**：将黑盒评分器转化为可读的逻辑表达式（尽管简单），使得定位和修复奖励黑客行为成为可能。这提示我们在设计自动化评估组件时，可解释性应作为一级安全需求。

## 关键术语表
*   **Verifier / Grader**：评分器/验证器，本文指对智能体单次输出进行 PASS/FAIL/ABSTAIN 判定的函数，是本文被演化的核心对象。
*   **Drawback Detector (op)**：缺陷检测器，验证器的原子组成单元，负责检查单一类型的失败模式，返回确定性或多为确定性的判决。
*   **Anchor Discipline**：锚点纪律，指验证器的选择和优化严格绑定到一小批固定的锚定参考样本，且从不使用目标任务的下游得分作为信号的核心安全原则。
*   **Birth Gate**：出生门控，新合成的操作符进入候选池的门槛，要求其能在一定比例的对应失败集群上触发，且在已知良好输出上保持干净。
*   **Shadow op**：影子操作符，由未标记数据缺口出生的新操作符，可参与计算共识但不能被直接选择，直到其在锚定集上证明价值后方可晋升。
*   **Double Ratchet**：双棘轮，本文提出的协同演化架构，指将验证器演化循环与生命周期管理的技能循环（采用 Ratchet 框架）配对交替运行。
*   **Validaty Gate**：有效性门控，选择过程中的守卫条件，丢弃在所有输入上都产生全通过、全失败或全弃权判决的退化表达式。
*   **Failure Capsule**：失败胶囊，一次失败的尝试及其错误文本组成的结构化记录，用于驱动下一个周期的技能合成。

## 可复现要素
*   **数据集**：MBPP+、Spider 2.0-Snow、内部报告生成任务。MBPP+ 和 Spider 2.0 为公开基准，报告生成任务数据未公开。Spider 2.0 需访问其托管的 Snowflake 仓库。
*   **代码/权重**：论文未明确声明代码开源仓库，但附录 G 说明每个运行都会将完整历史（JSON/SQLite）本地化存储，包括所有判定和 trace，支持重新计算统计检验。实现语言为 Python 3.12。
*   **关键超参**：dev 集大小固定为 10 项；选择目标函数中，dev 召回权重 FAIL:CLEAN=2:1；共识加权指数 w 在代码/SQL 任务为 1.0，报告任务为 0.25；复杂度惩罚系数 λ 为 0.001/0.002（按操作符类型）；技能循环运行 100 轮，验证器阶段轮数递减为 15/8/5/2。

# 论文速读：ToolBottleneckBench-Measuring-Tool-Agent-Performance-under-C

## 一句话总结
论文提出了 ToolBottleneckBench，一个在固定 harness 预算下测量工具代理性能变化的基准，通过控制单一压力（工具目录、可见菜单、工作流、返回编码）来隔离各因素对成功率的影响，并发现可见菜单大小是导致性能下降的主因，且多数失败由 harness 限制（如 completion cap 截断）引起，而非模型决策错误。

## 研究问题与动机
1. **成功率分数混杂模型能力与 harness 预算**：工具代理的成功率分数同时反映模型能力和运行 harness 的预算限制（如 completion cap、episode budget），但现有基准无法区分两者对失败的责任归属。
2. **失败标签误导性强**：现有评估通常只记录第一个失败步骤（如“工具选择错误”），但实际可能是 harness 限制（如响应被截断）导致代理未能调用工具，标签仅反映评分顺序而非真实原因。
3. **缺乏控制性压力测量**：真实环境同时变化多个负载，而现有控制基准要么同时改变多个因素，要么不记录导致失败的 harness 限制，无法量化单一压力的独立效应及其与预算的交互。
4. **修复与配置切换的比较缺失**：实践中常面临“应用修复”与“切换模型配置”的选择，但缺乏系统框架评估何种干预在给定压力下更有效，以及修复是否优于更换配置。

## 核心贡献（创新点）
1. **提出 ToolBottleneckBench 基准，通过固定任务族并逐一变压力实现控制性实验**：使用确定性编译器生成匹配变体，每次仅改变注册目录（R）、可见菜单（V）、认证工作流（W）或返回编码（D）中的一个压力，从而孤立测量每个压力的影响；与现有基准同时变化多因素或依赖自然任务分布的做法本质不同。
2. **引入“失败记录”机制，联合报告第一个未满足义务与终止 harness 限制**：每个失败 episode 记录首个未满足义务（如 availability、selection）和终止 flag（如 completion cap truncation、budget exceedance），以区分模型决策失败与 harness 限制导致的失败；现有工作通常仅提供失败步骤标签，无法识别截断等隐性限制。
3. **设计修复协议并与配置切换进行系统比较**：测试针对各压力的四种修复（连接器优先路由、路由菜单、工作流提示、接口指南），并量化修复的激活指标（L、Γ、Σ、Δ）；将修复效果与切换到其他模型配置进行配对比较，发现只有改变工具可达性或执行主体的修复有效，而提示修复无效；相比仅评估修复效果的前人工作，本文提供了“修复 vs 切换配置”的决策框架。
4. **在 21 个配置上大规模评估，揭示可见菜单压力与 completion cap 截断的强关联**：发现可见菜单大小是唯一具有大惩罚的模型面向压力，且惩罚与截断率高度相关（Pearson r = −0.95）；将完成上限提高 16 倍可消除大部分菜单惩罚；现有基准未系统量化各压力与 harness 限制的共现效应。

## 方法详解
1. **任务族与匹配变体**：基准包含 36 个任务族，嵌套在 12 个合成企业意图（会计、邮件、文件、日历）中；每个任务族固定用户请求、事实值、正确答案、证据规则和工具集；确定性编译器通过改变一个压力生成匹配变体，例如菜单大小 V ∈ {8, 32, 128}，工作流复杂度 W ∈ {low, medium, high}。
2. **四种 assigned pressures**：
   - **注册工具目录 R**：目录大小变化（32, 512, 2048 个函数），使用冻结检索器（不依赖模型）返回 16 个工具的短列表，评估可用性 A（所需工具是否在短列表中）和选择 S（模型是否选中），成功率按意向治疗（ITT）计算为 A·S。
   - **可见工具菜单 V**：向模型展示的 schema 数量（8, 32, 128），操作工具始终包含在内，额外添加路线邻居作为干扰项；schema 字节数从 3,481 增至 55,176。
   - **认证工作流 W**：工具程序的最小调用链长度（low: 2 次读取，high: 6 次读取），依赖深度和上下文累积随之增加。
   - **返回状态编码 D**：工具结果以四种编码返回（raw JSON、compact 字典编码、typed 类型化对象、linked 带链接的类型化对象），所有编码解码后值相同。
3. **固定 harness 合同**：所有主要结果使用同一固定 harness 预算：完成上限 1024 tokens/请求、episode 预算 128,000 tokens、调用限制 = 认证最小值 +2、轮次限制 = 调用限制 +2；存在不可行停止（当成功在调用限制内已不可能时提前终止）。
4. **验证任务成功（VTS）**：定义九个义务的合取 Y = A ∧ S ∧ P ∧ Q ∧ E ∧ X ∧ G ∧ B ∧ C，按顺序检查第一个未满足义务；任何依赖顺序的合法调用序列均被接受，无需模型裁判。
5. **失败记录**：记录（第一个未满足义务，终止 flag）配对；终止 flag 优先级为：(i) completion cap 截断、(ii) 超过 episode 预算或调用限制、(iii) 轮次限制、(iv) 不可行停止、(v) 错误结论、(vi) 其他合同违约。
6. **修复评估协议**：计算损失 L = μ_{ℓ0}^0 − μ_{ℓ1}^0（压力下的性能下降）、应力增益 Γ = μ_{ℓ1}^ℓ − μ_{ℓ1}^0（修复在压力下提升）、选择性 Σ = Γ − (μ_{ℓ0}^ℓ − μ_{ℓ0}^0)（修复在压力下 vs 无压力时的额外增益）、wrong-layer 优势 Δ = Σ − max_{k≠ℓ} Σ^k；修复激活需 L、Γ、Σ 均为正（经 Holm 校正）。
7. **配置切换比较**：将每个修复与所有其他配置切换进行配对比较，评估成功 superior、成本 superior 和 Pareto 非支配情况；使用 95% 置信区间判断差异显著性。

## 实验与结果
1. **数据集与评估配置**：36 个任务族、12 个意图，共 26,576 个评分条件；评估 21 个配置（来自 7 个组织：Anthropic、OpenAI、Google、Alibaba、DeepSeek、腾讯、Z.ai），所有配置通过托管推理端点运行。
2. **压力效应**：
   - **可见菜单 V**：菜单从 8 增至 128 使 VTS 下降 12.3 pp [95% CI: −14.6, −9.9]；全菜单保持可见时下降 17.5 pp；34/36 任务族性能下降。
   - **工作流 W**：低→高仅变化 +0.8 pp [−1.2, 2.8]，无显著聚合效应，但跨配置效应相反（Gemini 3.6 Flash −30.6 pp，HY4 Preview +34.7 pp）。
   - **返回编码 D**：compact 编码降低 VTS 3.7 pp [−5.7, −1.9]，但精确符号检验不支持（Holm p = .068）；typed 和 linked 无显著影响。
3. **截断与菜单惩罚的关联**：在 21 个配置中，V 效应与 V=128 时的截断率高度负相关（Pearson r = −0.95）；在 6 个截断严重配置中，将完成上限提高 16 倍（至 16,384 tokens）使菜单惩罚从 −43.7 pp 降至 −2.7 pp，交互效应 41.0 pp [36.2, 45.5]。
4. **失败 census**：20,408 个精确评分 episode 中，3,725 个失败（18.3%）；其中 91.5% 以 harness 限制结束（50.0% 超预算/调用限制、28.7% completion cap 截断、12.8% 不可行停止）；所有 849 个“selection”失败均无工具调用（838 个被截断）。
5. **修复激活与比较**：
   - **激活修复**：连接器优先路由（针对 R，Holm p = .001）、路由菜单（针对 V，Holm p = .003）、公共交接控制器（针对 W，Holm p < .001）激活；提示修复（工作流、接口）均未激活（Holm p = .949）。
   - **vs 配置切换**：路由对所有 21 个基线配置成功 superior；控制器对 17 个基线成功 superior 且对 4 个成本 superior；路由菜单仅 9/21 配置 Pareto 非支配；提示修复均无显著收益。
6. **外部验证**：在 ToolSandbox 环境中，更大菜单主要增加 token 消耗（+16,916 tokens）而非成功率下降（−0.5 pp），表明菜单压力在不同评估场景下影响模式不同。

## 相关工作脉络
1. **工具使用基准测试**（Li et al., 2023; Yao et al., 2025; Trivedi et al., 2024）：通常同时变化工具目录、工作流和观察格式，无法分离单一负载影响；本文通过固定任务族并逐一变压力实现控制性测量。
2. **受控工具负载研究**（Shi et al., 2025; Babu and Iyer, 2026b; Maekawa et al., 2026）：研究特定负载（如菜单大小、依赖深度）但未同步记录导致失败的 harness 限制；本文引入失败记录机制，区分模型决策失败与 harness 限制。
3. **Harness 效应分析**（Yao et al., 2026; Kapoor et al., 2026; Zhang et al., 2026）：关注 harness 变更对模型排名的影响，但不量化受控压力与 harness 限制的共现程度；本文直接测量每个压力效应中多少发生在特定 harness 限制之下。
4. **失败诊断与修复**（Raj et al., 2026; Chen et al., 2026b; Chen, 2026）：定位失败阶段并提出修复，但未与配置切换进行比较；本文提出修复协议并与所有配置切换进行成本/成功比较，提供实践决策依据。
5. **ToolMenuBench**（Babu and Iyer, 2026b）：区分黄金工具可见与选择，但未考虑 harness 限制；本文在相同框架下扩展，加入 harness 限制记录与压力交互分析。

## 局限性与未来方向
1. **固定 harness 预算**：结果仅在固定 episode 预算（128k tokens）和调用限制下成立；仅完成上限被系统变化，未测试 episode 预算或调用限制作为独立压力的效应。
2. **单次运行变异**：每个核心容量单元仅一次运行，虽通过家族 bootstrap 吸收变异，但未在更多配置上重复以评估随机性；sentinel repeats 显示 12.1% 的不一致率。
3. **合成环境与英文提示**：任务完全合成且精确分级，无部分信用；提示为固定英文文本，可能限制跨语言或真实场景的泛化性。
4. **配置耦合**：每个配置将模型与提供商路由绑定（如 FP4 量化路由），结果仅描述该配对，无法完全分离模型能力与路由效应。
5. **未来方向**：可扩展测试 episode 预算和调用限制作为可变压力；可集成真实工具服务器和更复杂的任务；可进一步分析不同配置下的成本效率权衡。

## 研究启发与可借鉴点
1. **控制变量设计可迁移**：通过固定任务族并使用确定性编译器生成匹配变体，每次仅改变一个压力，可隔离因素影响；此方法适用于评估其他 AI 系统（如多智能体协作、RAG 管道）中的特定模块负担。
2. **失败记录机制增强诊断**：联合报告第一个未满足义务与终止限制，提供比单一失败标签更丰富的诊断信息；可借鉴到 agent 评估中，帮助区分模型能力缺陷与基础设施限制。
3. **修复与配置切换比较框架**：提出的量化指标（L、Γ、Σ、Δ）和激活检验为评估干预措施提供了系统方法；本团队可结合此框架评估提示工程、架构调整或预算重新分配的效果。

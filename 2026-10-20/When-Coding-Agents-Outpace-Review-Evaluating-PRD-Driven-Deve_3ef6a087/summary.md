# 论文速读：When-Coding-Agents-Outpace-Review-Evaluating-PRD-Driven-Deve

## 一句话总结
本文引入 **PACE-Bench**，一个面向企业成熟仓库（brownfield）中 PRD 驱动增量开发的代码代理评测基准，通过 43 个生产任务、750 个专家审计的 Code Points 和分层语义评估协议，系统测量代理对完整产品需求文档（PRD）的完成情况，并将交付缺口与代理行为轨迹关联。

## 研究问题与动机
- **现有基准覆盖不全**：Issue resolution（如 SWE-bench）和 from-scratch 开发（如 DevEval、PRDBench）均未充分研究“在已有成熟仓库中增量完成 PRD"这一典型企业场景。
- **孤立测试不足以评估 PRD**：仅凭单元测试通过率无法证明代理满足了所有 PRD 条件、业务约定与集成需求；端到端测试又需高昂的服务与数据重建成本。
- **LLM judge 的稳定性与可信度存疑**：judge 决策可能依赖标准与证据的呈现方式，需确保在固定需求和实现时输出稳定。
- **单一分数难以指导改进**：相同分数可能对应不同未满足需求与不同执行失败模式，需结合轨迹信号与质量观察形成可追溯诊断，才能指导 harness 或模型优化。

## 核心贡献（创新点）
- **提出 PACE-Bench 基准**：将企业开发记录转化为可审计的冻结接受契约（750 个专家审计的 Code Points），实现从 PRD 到增量代码变更的端到端评估，区别于仅依赖测试执行或从 scratch 构建的已有基准。
- **设计噪声过滤双向准则合成方法**：独立从 PRD（需求视角）和参考 diff（实现视角）提取行为，交叉核查后精炼为原子 Code Points，去除偶发重构与重复项，保证契约 grounding 而不引入生成代码带来的命名强制。
- **建立可审计的三层评估协议**：L0（确定性结构校验）、L1（有界调用图证据定位）、L2（受限语义判定）组合，配合确定性聚合与加权计分，使得 judge 裁决有据可查且与专家共识高度一致（95.2%，κ=.945）。
- **提供可追溯的交付诊断与 harness 改进闭环**：将加权接受损失分解为不完整实现、缺失集成等四类症状，并与检索、编辑、验证等轨迹信号联动，展示如何通过诊断指导 harness 迭代（三次迭代提升均分 3.67 分，平台月度代码采纳率由 64.76% 升至 86.37%）。

## 方法详解
- **意图保留的 PRD 重构**：合并多轮对话、最终 diff 与元数据，生成独立 PRD；仅由生成代码引入的名称不作为强制约束，确保所有代理接收到统一的最终需求。
- **噪声过滤双向合成**：公式 (1) 定义独立提取 $E_R(R^\star)$ 与 $E_\Delta(\Delta_r)$，经 Reconcile 交叉核查过滤偶然变更，再经 Refine 拆分为原子 Code Points，最后由业务专家审核 grounding 与覆盖度。
- **三层评估协议**：
  - **L0**：机械验证明确约束，仅当证据确凿时判 Missing，否则降级至 L1，避免误拒。
  - **L1**：通过有界调用图扩展收集候选代码与集成上下文，记录完整证据包（声明、方法体、diff、连接边），检索命中本身不授予功能信用。
  - **L2**：在冻结契约与证据包基础上进行语义判定，允许等效实现，每条准则给出引用证据与严重性，输出 Covered/Partial/Missing。
- **确定性聚合与加权计分**：公式 (2) 计算得分 $S_c = 100 \frac{\sum w_i \phi(y_i)}{\sum w_i}$，其中 $\phi$ 映射 Covered=1、Partial=0.5、Missing=0；完整交付需 $S_c \ge 95$ 且无 Missing。
- **症状-信号归因框架**：将每个非 Covered 点的加权损失 $w_i(1-\phi(y_i))$ 分类为合同不匹配、集成/注册缺口、测试交付缺口、不完整实现四类症状；轨迹信号独立记录检索、编辑、验证事件；质量观察描述命名、架构、测试覆盖等，三者分离以防干净命名但未连接的组件获得功能信用。

## 实验与结果
- **数据集**：43 个企业生产任务，750 个专家审计 Code Points；参考变更中位数为 1,465 行/15 文件。
- **基线模型-脚手架**：8 个主模型（GPT-5.6-Sol、GLM-5.2、Qwen3.7-Max 等）共用 OpenHands 脚手架，另加 GPT-5.6-Sol(Codex)、Qwen3.7-Max(QwenCode)、Qwen3.8-27B 共 11 个配置。
- **主要结果**：统一脚手架下均分区间 52.1–78.1；**GPT-5.6-Sol 最高均分 78.08±2.71，完整交付率 14.0%**（6/43 任务）。原生脚手架中 Codex 与统一 GPT-5.6-Sol 完整交付率同为 14.0%，但 QwenCode 将 Qwen3.7-Max 完整交付率从 7.0% 提升至 11.6%。
- **难度因子**：派生/隐式 Code Points 占比与得分强相关（<25% 组 75.0、25%–50% 组 61.6、>50% 组 56.8，相差 18.2 分），而代码行数、文件数、PRD 长度等与得分相关性弱（$|\rho| \le .083$）。
- **评估可靠性**：正向对照（接受参考 patch）均分 98.35；负向对照 A-D 得分 0.00–4.03。与独立专家共识一致率达 **95.2%**，κ=0.945，无严重 Covered–Missing 反转；全流水线相比最强基线（Agent-as-a-Judge，78.0%）提升 17.2 个百分点。
- **重复稳定性**：Qwen3.7-Max 三次执行均分波动 SD=8.77，而对固定 patch 的三次 judging 记录 SD=2.36，执行变异约为判定的 3.7 倍。
- **静态知识注入**：在 28 个任务上比较无知识、仅定位器、仓库匹配知识、共享长上下文四种输入，增益在 -1.51 至 +0.69 分之间，**无稳定提升**。
- **Harness 改进闭环**：基于诊断实施检索策略修复等改动，Opus-4.5 三次发布均分从 59.37 升至 63.04（+3.67 分）；平台月维度代码采纳率由 64.76% 升至 86.37%，平均需求交付时间由 30.36 天降至 14.03 天。

## 相关工作脉络
- **SWE-bench / SWE-bench Pro**：基于 issue 描述的仓库级补丁修复，依赖单元测试/回归测试，无生成接受准则；PACE-Bench 聚焦 PRD 驱动的增量功能开发并引入人工审计的接受契约。
- **DevEval / PRDBench**：使用 PRD 输入但面向 from-scratch 新项目；PACE-Bench 针对 brownfield 成熟仓库，变更规模中位达 1,465 行/15 文件，更贴近企业真实增量场景。
- **FEA-Bench / FeatureBench**：面向特征请求与仓库级代码生成，依赖单元测试；PACE-Bench 结合 PRD 与多层语义判定，不依赖测试执行作为打分 oracle。
- **Harvest**：从生产 prompt 构建并依赖测试失败率评估；PACE-Bench 通过双向准则合成与专家审核构建冻结契约，实现 criterion-level 可审计评分。
- **CodeJudge / Agent-as-a-Judge**：前者评估代码偏差，后者自主搜索工作区评判；PACE-Bench 的 L2 judge 在固定契约与局部证据下运行，避免自主搜索引入的不稳定性，并与专家共识对齐至 95.2%。
- **Trail / 轨迹归因研究**：侧重执行失败定位；PACE-Bench 将轨迹信号（检索、编辑、验证）与加权接受损失症状显式关联，形成可操作的诊断-修复闭环。

## 局限性与未来方向
- **数据来源局限**：基准任务源于内部真实用户-代理交互记录，未探索直接从 merge request 挖掘或从仓库结构推导任务的替代构建路径，可能覆盖不同类型的开发任务。
- **静态知识注入效果有限**：在当前固定上下文预算与注入方式下，仓库知识、工程文档等未带来稳定增益，但论文承认结论仅适用于该设置，未来可研究知识如何更有效地进入执行流程。
- **单一脚手架与模型范围**：主要实验基于 OpenHands 脚手架与 8 个主流模型，原生脚手架对比虽显示 harness 影响，但更广泛的生态适配性有待验证。
- **专家审核成本高**：750 个 Code Points 需业务域专家与技术人员双重审核，规模化扩展至更大任务集时成本显著。

## 研究启发与可借鉴点
- **双向准则合成范式**：独立从需求与实现两个视角提取、交叉核查再精炼为原子契约，可有效过滤噪声并保证 acceptance criteria 的 grounding，可迁移至其他代码生成评测场景。
- **分层评估协议（L0-L2）**：将机械校验、证据定位与语义判定解耦，兼顾确定性与灵活性，且通过固定契约与局部证据显著提升了 judge 与专家的一致性，可作为 LLM-as-a-Judge 的通用设计参考。
- **症状-信号归因框架**：将结果缺口（四维症状）与过程轨迹（检索/编辑/验证信号）及质量观察分离记录，既避免命名等表面属性干扰功能评分，又为 harness 迭代提供可追溯的诊断线索，适合用于代理系统的持续改进闭环。
- **Harness 改进的可重复评估流程**：使用冻结任务集与冻结 Code Points 对 successive harness releases 进行对照评估，以微小均分提升（+3.67）验证诊断有效性，并反映到平台级运营指标（采纳率、交付时间），为工程实践提供了可量化的迭代评估范式。
- **难度因子的重新定义**：揭示“派生/隐式准则占比”比代码规模更能预测模型表现，提示后续研究应关注需求理解的复杂度而非单纯的任务体量。

## 关键术语表
- **PACE-Bench**：PRD-Anchored Coding-agent Evaluation，面向企业仓库 PRD 驱动增量开发的多层语义评估基准。
- **Code Point**：原子化、带权重与来源的可审计接受准则，由专家审核冻结，用于 criterion-level 评分。
- **PRD（Product Requirement Document）**：融合业务规则、边界条件、技术约束与验收标准的完整需求文档。
- **Brownfield repository**：已有成熟代码库，区别于 from-scratch 的新建项目。
- **Harness**：编码代理的运行框架，含检索策略、工具指导、规划与澄清逻辑等。
- **L0/L1/L2 三层评估**：L0 确定性结构校验、L1 有界调用图证据定位、L2 受限语义判定，逐层递进形成可审计评分。
- **症状-信号归因**：将未满足的加权接受损失归类为四类症状，并与轨迹中的检索、编辑、验证事件联动以支持诊断。
- **pass@k / pass$^k$**：pass@k 表示 k 次运行中至少一次覆盖的 Code Point 比例；pass$^k$ 表示 k 次运行中每次均覆盖的比例。

## 可复现要素
- **数据集**：43 个企业生产任务与 750 个 Code Points；生产需求文档、仓库快照与开发记录受组织访问控制限制，**未公开**；基准构建与评估代码、契约 schema、计分逻辑已开源。
- **代码/权重**：代码开源地址 `https://github.com/TianqiLiu1/PACE-Bench`；冻结的 Code Points、权重、基础修订版与候选 patch 哈希在评估期间固定。
- **关键超参**：OpenHands 1.21.0 脚手架，迭代上限 200，工具并发度 4；语义 judge 为 Opus-4.8，最大输出 8,192 tokens；Qwen 生成努力度设为 xhigh；完整交付阈值 $S_c \ge 95$ 且无 Missing。
